# Protocol compatibility audit

Use this register to turn protocol review into a repeatable loop: discover a
concrete issue, record its evidence and priority, fix one item, run the relevant
checks, and record the commit that closes it.

## Findings

| ID | Protocol | Finding and evidence | Priority | State |
| --- | --- | --- | --- | --- |
| FTP-001 | FTP | FTP keyed failed-login counters by the raw USER argument, while HTTP and WebDAV normalized login identifiers. Since credential verification accepts case-insensitive email addresses, changing email casing created fresh FTP counters and bypassed the configured per-source throttle. All three entry points now use one shared key builder with trimmed Unicode lowercase normalization, and FTP uses libunftp's socket peer IP. | P1 | Regression verified by `88b84ff` |
| FTP-002 | FTP | libunftp 0.23.0's control-channel codec buffered input until a newline without a maximum frame size. An unauthenticated client could keep sending a single command line and grow per-session memory despite the connection-count and idle-time limits. The vendored codec now rejects frames over 8 KiB, bounding each control-channel buffer. | P1 | Regression verified by `4774ade` |
| FTP-003 | FTP | Self-signed FTPS certificate setup followed existing symlinks: it could chmod a private-key symlink target or chmod an unrelated directory when the certificate directory itself was a symlink. Startup now rejects symlinked/non-directory parent components and non-regular certificate/key paths, creates new directories with private permissions, preserves existing directory permissions, rejects group/world-writable key directories, and tightens private-key permissions through an opened file handle. | P2 | Regression verified by `08a998b`; key-file and directory symlink targets remain untouched |
| FTP-004 | FTP | FTP authentication cloned the plaintext PASS value into another String, and self-signed certificate creation kept serialized private-key PEM in an ordinary String after writing it. Authentication now borrows the credentials value, while PEM is held in a zeroizing SecretBox that clears it when dropped; this reduces extra secret copies without claiming to erase libunftp's original credential buffer. | P2 | Fixed in code; regression verification pending |
| FTP-005 | FTP | FTP path normalization allowed control characters, and LIST converted stored paths without revalidating them. A name created through another protocol could therefore place terminal control bytes into an FTP directory listing. FTP now rejects control characters in requested and listed paths. | P2 | Regression verified by `47d68ad`; LF, CR and ESC are rejected from normalized paths |
| FTP-006 | FTP | FTP LIST/NLST paged every child row into a single Vec with no total bound. A large directory could therefore consume unbounded session memory, and several concurrent listings could exhaust the process. Listings now stop at 20,000 entries or an estimated 8 MiB of metadata, and use 100-row query pages. | P1 | Regression verified by `b5307f9` |
| FTP-007 | FTP | Each legacy PASV/EPSV spawned a task holding a passive listener for up to 15 seconds. Repeating the command could occupy the configured port range and prevent subsequent transfers. A new PASV/EPSV or successful PORT now cancels the previous listener and waits for its socket to close; accepted listeners are dropped before transfer processing begins. | P1 | Regression verified by `6a0eae1` |
| FTP-008 | FTP | FTPS data-channel enforcement checked PASV but missed EPSV and active PORT, and it allowed PROT C after allocating a protected passive listener. Clients could therefore negotiate a clear data channel on a server configured to require FTPS. The middleware now rejects PROT C for FTPS-required accounts and checks data-channel protection for PASV, EPSV and PORT; the Accounts policy checks data TLS for non-anonymous users. | P1 | Regression verified by `b294819` |
| FTP-009 | FTP | The control line was bounded, but the FTP path model had no length limit. Repeated CWD operations into deeper directories could keep growing per-session working-directory state and PWD/STAT responses. FTP path normalization now rejects paths over 4 KiB before storing or querying them. | P2 | Regression verified by `a12c423` |
| FTP-010 | FTP | The reply codec wrote dynamic single-line and multiline text directly to the control socket, and raw USER/path values entered log fields. Control characters in those values could forge replies or inject terminal controls into clients and logs. USER now rejects control characters, while reply text and username/path log fields replace control and Unicode line-separator characters with spaces. | P2 | Regression verified by `1987ee5`; dynamic single-line and multiline text cannot add reply lines |
| FTP-011 | FTP | PASS returned immediately after spawning an authentication task and left the session in `WaitPass`. A client could pipeline many PASS commands to create unbounded authentication tasks and database lookups before the shared password-work gate. The session now moves to `Authenticating` before spawning and rejects further PASS/USER attempts until the result returns it to `New` or `WaitCmd`. | P1 | Regression verified by `559deff`; 32 concurrent PASS attempts spawn one authentication attempt |
| FTP-012 | FTP | Unauthenticated sessions could keep the configured idle timeout alive indefinitely by sending NOOP, and an AUTH TLS handshake could wait without a deadline. The control loop now applies an absolute authentication deadline capped at 60 seconds (or the shorter idle timeout) and applies the remaining deadline to the initial TLS handshake. | P1 | Regression verified by `76580ec`; repeated pre-login NOOPs do not extend the deadline |
| FTP-013 | FTP | After a data socket was accepted, libunftp waited up to five minutes for the transfer command and marked the session busy, suppressing the control idle timeout. Data-channel TLS accept also used `unwrap()`, so malformed or stalled handshakes could panic before clearing that busy state. The command wait is now 60 seconds; data TLS handshakes time out after 15 seconds and report a connection failure so the session clears its busy state. | P1 | Regression verified by `0f8bd41`: malformed and stalled passive TLS candidates are rejected and a valid resumed session completes the transfer; `2743d43` verifies QUIT cancels an accepted data worker waiting for its command. |
| FTP-014 | FTP | PASS authentication ran in a detached task that could outlive QUIT, a control timeout or a disconnected client, continuing database and password work after its session ended. The task now observes closure of its control-message channel and cancels the pending authentication future when that session closes. | P1 | Regression verified by `31bd0d8`; disconnect cancels an in-flight delayed authentication |
| FTP-015 | FTP | RMD checked for children before flushing the session's pending upload batch, then called the generic recursive delete service. A pending or concurrent upload could therefore appear after the check and be deleted by RMD. RMD now flushes first, then SQLite checks for descendants and deletes only the directory inside one `BEGIN IMMEDIATE` transaction; FTP reports a non-empty result correctly and HTTP/WebDAV map this domain conflict to `409`. | P1 | Regression verified by `450cb5a`; RMD flushes a below-threshold upload batch and preserves the non-empty directory |
| FTP-016 | FTP | The data socket had a 60-second wait for the transfer command, but once STOR/RETR/LIST started, a peer could stop sending or stop reading indefinitely. The session stayed marked data-busy, bypassing its control idle timeout and occupying one of the global connection slots. Data streams now time out after 60 seconds without read/write progress and reset the deadline when bytes move. | P1 | Regression verified by `968694b`; stalled reads and below-rate writes time out |
| FTP-017 | FTP | A control connection could repeatedly request passive ports and connect data sockets while earlier data workers were still waiting for a transfer command. The global connection cap counted only control sessions, so one authenticated session could create many socket-owning tasks during the 60-second wait. Replacing a passive listener now waits for its task to finish, refuses a new listener while a transfer is active, and the data worker closes any additional socket for a busy session. | P1 | Regression verified by `0417b42`: after a resumed data socket is accepted, twelve repeated EPSV requests each return `425` until the session clears the waiting worker. |
| FTP-018 | FTP | QUIT or a dropped control socket ended `Server::service` while detached passive-listener/data-worker tasks could remain alive for up to 60 seconds. The outer connection semaphore was then released, so a client could repeat connect/authenticate/PASV/disconnect and accumulate work beyond the configured cap. Control shutdown now cancels and joins the legacy passive listener and awaits the session's data worker before releasing the connection slot. | P1 | Regression verified by `4a5b759`; QUIT closes EPSV listener and frees the one-session slot |
| FTP-019 | FTPS | Passive data sockets were matched to the control connection only by source IP, without checking whether the TLS peer belonged to that FTP session. A client on the same NAT/LAN could race the passive port and use its own server-authenticated TLS session as the data channel. Each control session now has an isolated TLS session cache and ticket key; the data channel must resume that control TLS session, rejecting tickets from other sessions and full handshakes. FTPS clients must support TLS session reuse. | P1 | Regression verified by `814a157`: a second FTPS control session races the victim's EPSV listener, and the victim still completes a protected directory transfer. |
| FTP-020 | FTPS | `AUTH TLS` remained available after the control channel was already encrypted. Repeating it made the server wrap another TLS stream around the existing one, allowing authenticated clients to grow per-session TLS state without bound. The command now returns `503` once the control channel is protected. | P1 | Regression verified by `13e2e37` |
| FTP-021 | FTP auth | Password verification succeeded for an account rejected by the FTP role filter, but the resulting login rejection did not increment the shared failed-login limiter. Someone with such an account could repeatedly trigger password-hash work without reaching the per-IP/login threshold. These role-filter rejections now count as failures and remain subject to the shared limiter. Disabled accounts are rejected by `AuthService` as invalid credentials and already count through the normal failure path. | P2 | Regression verified by `22aef24`: a valid-password role rejection consumes the only attempt; after changing the user to an allowed role, the same source/login remains throttled. |
| FTP-022 | FTP | On abrupt disconnect, the storage backend submitted a pending snapshot batch from `Drop` in a detached task. The control service could return and release its connection slot before that task finished, letting repeated short FTP sessions accumulate background commits beyond the connection cap. The batch task now retains that session's semaphore permit until the commit finishes. | P1 | Regression verified by `e89e9a4`: with SQLite connections held, abrupt disconnect keeps the only FTP slot unavailable until the pending snapshot commits; the slot is then released. |
| FTP-023 | FTP | Several authenticated control commands spawned detached metadata or mutation tasks and returned immediately. A client could pipeline SIZE/MDTM/DELE/MKD/RNFR/STAT requests faster than storage operations completed, creating unbounded per-session task and database work. These handlers now share a four-task per-session permit pool and return `451` when it is full. | P1 | Regression verified by `c3dbbad`: with SQLite operations blocked by a saturated pool, the fifth pipelined SIZE receives `451` while four tasks are still in flight. |
| FTP-024 | FTP auth | Login throttling keyed failures by source IP plus username only, allowing password spraying across many usernames from one source to bypass the threshold and keep password verification workers busy. The shared limiter now also aggregates failures by source IP at ten times the configured per-login threshold across FTP, HTTP and WebDAV; successful logins clear only their own login counter. | P1 | Regression verified by `9077635`: ten distinct bad usernames from one source cause the subsequent correct FTP login to be rejected by the aggregate source limit. |
| FTP-025 | FTP auth | FTP treated every `AuthService::verify_credentials` error as a bad password. When the shared password-work semaphore was saturated, its `RateLimited` error therefore incremented login-failure counters for valid users and could lock out accounts during load. Only `InvalidCredentials` now increments the brute-force limiter; operational/auth-service errors return a generic temporary authentication failure instead. | P1 | Regression verified by `919fbab`: `RateLimited` leaves the per-login and per-source counters clear, while `InvalidCredentials` still consumes the configured attempt. |
| FTP-026 | FTPS | Self-signed certificate setup validated the final key directory, but did not reject writable ancestor directories. A local user could replace the checked directory between validation and opening the certificate/key path. Startup now rejects symlinked ancestors and group/world-writable ancestor directories, allowing sticky directories such as `/tmp` only as containers for a private leaf directory. | P2 | Regression verified by `01cb213`; group-writable ancestors are rejected without creating certificate files |
| FTP-027 | FTP | The passive-port selector computed `end - start` and used that as a modulo divisor, even though configuration permits a one-port inclusive range such as `50000-50000`. A PASV/EPSV request with that configuration could panic on division by zero; the selector also never chose the configured upper endpoint. It now calculates the inclusive range size using wider integer arithmetic and visits every configured port. | P2 | Regression verified by `814730a`; single-port and upper-end selection boundaries pass |
| FTP-028 | FTP | FTP rejected Unicode control characters in path segments, but U+2028 and U+2029 are Unicode line separators and do not satisfy Rust's `char::is_control`. A name created through HTTP or WebDAV could therefore appear as an extra line in FTP LIST/MLSD output on Unicode-aware clients. FTP path normalization now rejects both line separators as well. | P2 | Regression verified by `e60c126`; U+2028 and U+2029 are rejected in paths |
| FTP-029 | FTP auth | USER rejected control characters but accepted U+2028 and U+2029, which Rust does not classify as control characters. These values could reach PASS authentication, where the raw username was included in failure logs. USER now rejects both Unicode line separators before authentication starts. | P2 | Regression verified by `36af98f`; U+2028 in USER leaves authentication state unchanged |
| FTP-030 | FTP | The listener returned on service shutdown while each accepted session ran as an untracked task. `FtpServerHandle::wait()` could therefore finish and the main process could close the database pool while passive listeners or data workers were still running. FTP sessions now receive libunftp's shutdown notification, which runs its normal data cleanup; the listener tracks sessions and waits for all of them before returning. | P1 | Regression verified by `bafdd41`: shutdown with an active FTPS session and pending EPSV closes the control connection, waits for cleanup, and releases the passive port. |
| FTP-032 | FTP | The FTP backend commits a session's final upload batch in a detached `Drop` task. The task retained its connection permit, but service shutdown waited only for control-session tasks, then the main process could close the database pool while a final snapshot commit still ran. After draining sessions, the listener now waits to reacquire every connection permit, which also waits for detached final commits to finish before `FtpServerHandle::wait()` returns. | P1 | Regression verified by `77005d4`: with SQLite unavailable, `FtpServerHandle::wait()` stays pending after shutdown until the abrupt session's final snapshot commits. |
| FTP-033 | FTP auth | Unicode bidirectional formatting controls such as U+202E are not recognized by Rust's `char::is_control()`. An unauthenticated client could submit one in USER, reach PASS failure logging, and visually reorder the username and surrounding log fields. USER now rejects these controls, and FTP control-text sanitization replaces them in log and reply text. | P2 | Regression verified by `450957a`: USER with U+202E is rejected before authentication and the same control session can still log in with valid credentials. |
| FTP-034 | FTP | Session cleanup stopped polling the one-slot control-message channel, then awaited an active data worker. If another command had filled the channel, the worker could block sending its completion message while cleanup waited for that same worker. Cleanup now closes the receiver before joining passive listeners or data workers, causing pending result sends to fail and release the worker. | P1 | Fixed in code; regression verification pending |
| FTP-035 | FTP | An accepted passive data connection with no transfer command kept its data worker alive for the full 60-second command timeout. Control-session cleanup awaited that worker, so a client could delay FTP shutdown by holding idle passive connections. Cleanup now sends the worker's existing abort signal before joining it, making this idle case exit immediately. | P2 | Regression verified by `2743d43`: after FTPS accepts the passive TLS socket but before any transfer command, QUIT completes within three seconds and closes the data channel. |
| FTP-036 | FTP | FTP path validation rejected terminal controls and Unicode line separators, but allowed Unicode bidirectional formatting controls in names created through other protocols. FTP directory listings could therefore render filenames with deceptive visual ordering. FTP now rejects the Bidi_Control characters in both requested paths and stored paths before use or listing. | P2 | Regression verified by `b22a943`: normalization rejects U+202E and U+2066/U+2069 paths, covering both requested and stored path validation. |
| FTP-037 | FTP | APPE treated every metadata lookup failure as a missing file and continued with offset zero. A transient storage error for an existing file could therefore make the subsequent upload replace its contents. APPE now treats only `PermanentFileNotAvailable` as a new file; other lookup errors abort the transfer and reach the client. | P1 | Regression verified by `f73ec72`: after corrupting existing-file metadata, an end-to-end APPE fails without creating a version or changing the original blob bytes. |
| FTP-038 | FTP | After a data worker received RETR/STOR/LIST, it held the session mutex across the full transfer and stopped listening to ABOR. Control disconnect cleanup therefore could not acquire the session lock to signal the worker, and continuous transfers could delay shutdown. The worker now releases the lock before I/O and uses a shared cancellation token across FTPS handshakes and data reads/writes. | P1 | Regression verified by `374cb0a`: disconnecting control during a partial STOR closes its data socket, releases the only session slot, and leaves no entry or blob. |
| FTP-039 | FTP | DELE checked that the target was a file, flushed the session batch, then called the generic subtree delete service by path. A concurrent replacement with a directory during that gap could make DELE recursively remove the replacement and its contents. FTP now submits the observed entry ID and version as a conditional delete, so a changed target fails instead of deleting a different subtree. | P1 | Regression verified by `70a5d78`: a snapshot trigger replaces the observed file with a non-empty directory during DELE's flush, and the conditional delete fails while preserving the directory and child. |
| FTP-040 | FTP | FTP `metadata()` converted every current-version lookup failure into successful zero-byte metadata. APPE uses that metadata to choose its append offset, so a storage failure on an existing file could still make APPE overwrite it despite the missing-file check. Version lookup failures now propagate as FTP errors instead of masquerading as an empty file. | P1 | Regression verified by `97fe415`: a corrupted current-version size makes metadata return `LocalError` and leaves the file's current version unchanged. |
| FTP-041 | FTP | PWD wrapped the current path in quotes without escaping embedded quote characters. A directory name containing `"` therefore made the 257 response ambiguous and clients could recover the wrong working path. PWD now doubles embedded quotes in the pathname before returning it. | P2 | Regression verified by `aa7d5e3`: PWD on a directory containing `"` returns the quoted 257 pathname with the embedded quote doubled. |
| FTP-042 | FTP | MKD returned the created path in a 257 reply without quoting it or doubling embedded quotes. Clients could misparse the created path and operate on a different directory name. The reply now uses the RFC 959 quoted pathname form and doubles embedded quotes. | P2 | Regression verified by `8257787`: MKD's 257 reply quotes a path containing `"` with the embedded quote doubled, and CWD can use the exact created name. |
| FTP-043 | FTP | STOR wrote the full body to the blob store before discovering that an existing file occupied an ancestor path (for example, uploading `file/child`). The rejected upload left an unreferenced blob on disk until garbage collection, allowing repeated attempts to consume storage. FTP now checks existing path ancestors before reading the upload stream. | P1 | Regression verified by `b7d9316`: rejected STOR beneath a file leaves the blob-store file count and entry tree unchanged. |
| FTP-044 | FTP | When an upload failed after publishing a new content-addressed blob, the importer immediately deleted that blob. A concurrent upload could deduplicate to the same blob and commit a valid file before the failing import reached cleanup, leaving the successful file with missing content. Failed imports now leave the blob for the grace-period orphan collector, which checks references before deletion. | P1 | Regression verified by `6d5946a`: the precommit race deterministically commits a deduplicated copy, makes the first import fail on a directory conflict, and confirms the successful version's blob remains readable. |
| FTP-045 | FTP | STOR to an existing directory passed the parent-path check, so the backend consumed and stored the complete data stream before the importer rejected the destination. FTP now checks the destination entry together with its ancestors before reading the stream, while still allowing replacement of an existing file. | P1 | Regression verified by `788e939`; the test first exposed a root-level target check skipped when the path had no parent, then confirmed rejection leaves the blob store unchanged. |
| FTP-046 | FTP/storage | DELE released the final database reference and immediately removed the content-addressed blob file. A concurrent upload could already have observed that file for deduplication, then commit its reference after deletion, leaving the successful file unreadable. Released blobs are now kept through the configured grace period before orphan collection removes them; failed upload cleanups use the same deferral. | P1 | Regression verified by `a4cbc66`: an import deduplicates the existing blob, deletes its only source in the precommit window, then commits a new version that still reads the original bytes. |
| FTP-047 | FTP | FTP paths were limited to 4 KiB but had no directory-depth limit. A STOR or MKD path with thousands of segments could make parent creation perform thousands of sequential database lookups and writes in one command. FTP path normalization now caps paths at 256 segments across all commands. | P2 | Regression verified by `a12c423` |
| FTP-048 | FTP auth | FTP checked account status only during login, so an established session could keep reading or mutating files after the account was disabled or its credentials/role changed. Storage operations now reload the account and reject sessions whose enabled state, username, role, or update timestamps no longer match the login identity. | P1 | Regression verified by `8c44499`: password rotation revokes an established session before MKD, rejects the old password, and accepts the replacement password; disabled-account session checks are covered by adjacent tests. |
| FTP-049 | FTP | Control-channel replies had no write deadline. A connected client could stop reading, fill the TCP send buffer with replies, and keep the session blocked outside the control read timeout while holding a connection slot. The greeting and all command/error replies now have a 60-second write deadline; a stalled writer closes the session and runs normal cleanup. | P1 | Fixed in code; regression verification pending |
| FTP-050 | FTPS | Data TLS used the same per-control-session ticket issuer and writable session cache as the control handshake. Rustls issues tickets for a completed full handshake before `accept()` returns, so a same-IP client that raced a passive port could obtain a data-originated ticket and reuse it on a later transfer, passing the `HandshakeKind::Resumed` check. Data TLS now reads but cannot add control-session cache entries; ticket decryption marks valid control resumption, and the data ticket gate only reissues after such a resumption. | P1 | Regression verified by `673222b`: repeated attacker data handshakes remain full handshakes, while the victim's control-session ticket resumes and completes the listing. |
| FTP-051 | FTP/WebDAV | FTP `DELE` checked the observed file ID and version, but supplied no WebDAV lock snapshot to the conditional delete transaction. It could therefore delete a resource protected by an active WebDAV lock. FTP now rejects currently locked targets and submits an empty lock snapshot that SQLite rechecks atomically with the deletion. | P1 | Regression verified by `f2c47a0`: after SQLite stores an exclusive WebDAV lock on an uploaded file, FTP DELE fails and the file content remains intact. |
| FTP-052 | FTP/WebDAV | FTP `STOR` imported blobs through an unconditional version write, so a WebDAV lock acquired during upload could be ignored when the file version committed. FTP now rejects active locks before reading the data stream and passes the observed entry/version and lock snapshot to the SQLite version transaction for an atomic recheck. | P1 | Regression verified by `a68ea80`: acquiring a WebDAV lock after STOR preflight causes final commit to fail and preserves the original file content. |
| FTP-053 | FTP/WebDAV | FTP `RNTO` moved entries through the unconditional subtree move path, so it could relocate a locked file or directory and could move resources onto a locked destination. FTP now checks locks on each source and destination subtree path, then asks SQLite to recheck those path snapshots in the move transaction. | P1 | Regression verified by `15d5923`: RNTO fails for a locked source and a locked destination, with all entries and destination content preserved. |
| FTP-054 | FTP/WebDAV | FTP `MKD` created the target and any missing parents through unconditional entry inserts, so a locked null resource or a lock acquired during creation could be bypassed. FTP now checks every path component and creates each missing directory only when SQLite atomically confirms the path and lock snapshot are still current. | P1 | Regression verified by `169e56a`: MKD at a WebDAV-locked null resource fails without creating an FTP entry. |
| FTP-055 | FTP/WebDAV | FTP `RMD` used the atomic emptiness check but did not include WebDAV lock or observed-entry state, allowing an active lock to be ignored during directory removal. FTP now rejects locked targets and SQLite rechecks the directory identity, version, emptiness, and lock snapshot in the delete transaction. | P1 | Regression verified by `0d79345`: RMD of an empty directory under an active depth-infinity WebDAV lock fails and preserves the directory. |
| FTP-056 | FTP/WebDAV | FTP `STOR` could auto-create missing parent directories without checking a direct lock on a locked null resource in the path. Upload now snapshots every path component and creates missing parents and the file entry through SQLite's atomic conditional-create operation before the final version write. | P1 | Regression verified by `301e9bb`: STOR below a WebDAV-locked null parent fails without creating entries or publishing a blob. |
| FTP-057 | FTP/WebDAV | Directory lock snapshots covered existing entries but could miss WebDAV locks on lock-null URLs below an otherwise empty directory or inside a renamed subtree. RMD and RNTO now reject active descendant locks and SQLite rechecks that the affected source/destination subtrees remain lock-free in the mutation transaction. | P1 | Regression verified by `383e0d4`: a lock-null child prevents RMD of its empty parent and RNTO of the directory subtree. |
| FTP-058 | FTPS | A legacy PASV/EPSV listener accepted the first TCP connection and closed its port before checking that the peer IP matched the control connection. A remote scanner could connect to a guessed passive port first and abort the real transfer. The listener now drops foreign-IP connections and keeps accepting from the control peer until the existing 15-second deadline. | P1 | Regression verified by `138c6e3`: a `127.0.0.2` scanner connects first, then the same EPSV listener still accepts the owning session's resumed TLS transfer. |
| FTP-059 | FTPS | FTP-050 prevented a same-IP peer from hijacking a data connection without the control session's TLS ticket, but the legacy PASV/EPSV listener still closed after accepting that peer's TCP socket. It now completes the candidate TLS handshake and verifies control-session resumption before consuming the listener; invalid or stalled same-IP candidates are dropped and the listener continues accepting until its deadline. | P1 | Regression verified by `f1c1f8e`: after rejecting another control session's TLS handshake, the original EPSV listener accepts a resumed transfer from its owner. |
| FTP-060 | FTP | When active mode was enabled, PORT parsed numeric fragments permissively and connected to the client-supplied IPv4 address before checking the data peer, allowing FTP bounce scans and server-side connections to third-party hosts. PORT now requires exactly six decimal octets and rejects a target IP that differs from the control peer before opening any outbound socket. | P1 | Regression verified by `7b293f2`: strict parsing, peer matching (including IPv4-mapped IPv6), malformed parameters and third-party targets are covered before connect. |
| FTP-061 | FTP | Active PORT awaited `TcpStream::connect` without a deadline. A client could advertise a same-IP endpoint that silently dropped SYN packets and keep the command handler and session slot occupied for the operating system's much longer TCP timeout. Active data connects now time out after 15 seconds and return 425. | P1 | Fixed in code; regression verification pending |
| FTP-062 | FTP | When PASV advertised a configured DNS hostname, the command handler awaited the system resolver without a deadline. A stalled resolver could hold the control loop and its connection slot beyond FTP's idle timeout. PASV hostname resolution now has a five-second deadline and returns 425 on timeout. | P1 | Fixed in code; regression verification pending |
| FTP-063 | FTP | The control-channel logging middleware formatted raw command events, replies and errors with `Debug`, bypassing the sanitization already used for usernames and wire replies. A client-controlled path containing bidirectional formatting characters could therefore make log entries misleading before path validation rejected it. Event, reply and error debug text is now sanitized before logging. | P2 | Fixed in code; regression verification pending |
| FTP-064 | FTP | Command handlers and data workers also logged request paths directly, while automatic tracing spans recorded raw command arguments and `Debug` formatting of data-channel commands or failed channel sends could include their path payloads. Path and backend-error text is now sanitized in direct logs, command spans omit input arguments, and data-channel logs no longer format raw command or message payloads. | P2 | Fixed in code; regression verification pending |
| FTP-065 | FTPS | Pooled and PROXY-protocol passive listeners dispatched a same-IP TCP candidate to the data worker and removed its switchboard entry before checking control-session TLS resumption. A client sharing the control connection's NAT could occupy a guessed passive port and make the real transfer fail when TLS was eventually checked. Prebound listeners now require the bounded FTPS handshake and control-session resumption check before consuming the mapping; invalid candidates leave it available, and pending handshakes are capped globally and per session. | P2 | Fixed in code; regression verification pending |
| FTP-066 | FTP | In prebound listener modes, PASV assumed the control connection's destination address was IPv4 and used `panic!` for IPv6. An authenticated client connecting over IPv6 could therefore terminate the listener task by issuing PASV. The listener now rejects IPv6 PASV with a port-allocation failure before reserving a passive port. | P1 | Regression verified by `bdd6506`: IPv6 addresses take the controlled rejection path without panicking; IPv4 address selection remains intact. |
| FTP-067 | FTP | The storage backend decremented the global active-session counter when dropped, even if the client disconnected before authenticating and `enter` had never incremented that counter. Session teardown now decrements the counter only for sessions that entered the backend. | P2 | Fixed in code; regression verification pending |
| FTP-068 | FTP | RNTO validated the source and destination command paths but prepended the destination to every descendant path in a moved directory without reapplying FTP's byte-length, depth, and unsafe-character checks. ## Discovery and verification baseline

- Static analysis: `cargo clippy --workspace --all-targets -- -D warnings`.
- Formatting gate: `cargo fmt --all -- --check`.
- Regression baseline: `cargo test --workspace` plus protocol-specific end-to-end tests.
- Third-party tools found in the current development environment: `curl` 8.5.0,
  `rsync` 3.2.7 (protocol 31), `rclone` 1.60.1-DEV, `cadaver` 0.24,
  `boto3` 1.34.46, `botocore` 1.34.46, and `litmus`.
- Successful client probes are evidence for the operations listed above, not
  proof of complete protocol conformance. Remaining explicit gaps include
  Windows WebDAV clients, device/FIFO support and numeric ID mapping, and S3 power-loss/filesystem
  fault injection.

This is an environment snapshot, not a claim that the listed protocols are
fully conformant. Recheck tool availability and update this register when the
environment or test harness changes.
