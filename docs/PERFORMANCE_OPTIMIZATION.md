# HTTP 性能审核与优化记录

本文记录 HTTP 性能审核、已实施的改进和仍需结合部署负载判断的事项。审核基线来自 v2.6.11 代码；下方数字来自本地回环、合成数据或临时对照测试，不能作为生产环境 SLA。数据库设备、操作系统缓存、网络、请求分布和并发模型都会改变结果。

## 历史与快照浏览的读路径审核（v2.6.15 之后）

本轮针对「目录历史 / 快照浏览 / 侧栏概览」这类读操作复核了路由、服务与 SQLite 查询，测量基线如下。

测量环境：release 构建、本地回环、`journal_mode=WAL`；合成库为 50,050 个条目（50 个目录各 1,000 个文件）、40 个快照（2,002,000 条快照条目，约 1 GB）；历史库为 9,328 个快照、2,034,914 条快照条目。所有数字均为本机样本，不能作为生产 SLA。

| 操作 | 审核发现 | 改动 | 修复前 → 修复后（p50） |
| --- | --- | --- | --- |
| 快照内列目录（`GET /api/files/list?commit=…`） | 每次请求把请求路径下的整棵子树读进 CTE，按首段分组，再用临时 B-tree 排序；一页结果要跑两遍（计数 + 分页）。5 万条目的快照根目录约 42 ms，且随树大小线性增长 | `snapshot_entries` 增加由 `entry_path` 派生的虚拟列 `parent_path`，并建立 `(snapshot_id, parent_path, entry_path, change_type)` 索引；分页与总数来自同一次索引 seek（`COUNT(*) OVER ()`），越界页再补一次计数 | 根目录 41.7 ms → 0.51 ms；子目录 4.2 ms → 1.5 ms；8 并发 62.8 ms / 120 req/s → 6.6 ms / 1,138 req/s |
| 目录历史（`GET /api/history?path=<目录>`） | 取最新一页本身只需要按 `created_at` 倒序 seek；但默认还会对整段历史统计 `totalCommits`（每个快照两次 B-tree 探测），并发下吞吐降到约 45 req/s，而界面并不使用该总数 | 目录历史默认不统计总数，需要时传 `with_total=true`；文件历史的总数仍始终返回（按条目版本索引计数） | 9,328 个快照的目录：计数 + 分页 108 ms → 4.3 ms（顶栏只取一页时 0.1 ms）；不存在的路径 416 ms → 56 ms |
| 侧栏概览（`GET /api/files/overview`） | 文件数、目录数、总字节、分类占比与最近更新分三次聚合，每次都为每个条目用相关子查询取当前版本（5 万文件约 22 万次索引探测）；「最近更新」还对每个文件的版本时间戳排序 | 统计与分类合并为一遍聚合（每个条目只取一次当前版本）；「最近更新」改按 `entries.updated_at` 排序并使用 `(namespace_id, updated_at DESC) WHERE kind='file'` 部分索引 | 144 ms → 69 ms（5 万文件）；8 并发 2.5 s / 3 req/s → 0.72 s / 11 req/s |
| 顶栏版本步进（前端） | 请求不可取消，切换目录时旧请求的 `finally` 因序号不匹配不会复位 loading，顶栏可能一直停在「加载历史...」；失败后没有可见反馈 | 请求带 `AbortController` 与 15 s 超时，切换目录/重复触发会取消上一笔并立即复位 loading；失败显示「加载失败」并在悬停提示给出原因，再次点击立即重试；无快照时显示「无历史」 | 修复前会长时间停留在加载态；修复后请求被取代即复位 |

### 已验证并保留的现状

| 项目 | 证据 | 处理 |
| --- | --- | --- |
| 实时目录列表的分页与总数 | 5 万条目、单目录 1,000 个文件时，一页 200 条约 9 ms；根目录计数使用部分覆盖索引；嵌套目录的计数需要扫描该目录的子树 | 保留。目录内的条目数通常有限，子树计数与「加载更多」的游标分页一致；未发现界面等待证据 |
| 文件名搜索 | 5 万条路径、单次约 6–12 ms；服务端限制候选数量与读取预算 | 保留现有上限。并发 8 时约 180 ms / 42 req/s，属于有界扫描的预期成本 |
| SQLite 连接池 | 已有记录：10 个连接为混合读写折中，增加到 20 个对读延迟收益约 8%–10%，但写入 p95 变差一倍以上 | 保留 10 |
| 每请求鉴权 | 每次请求 2 次索引点查（会话、用户），`last_seen` 每会话每分钟最多写一次 | 保留；未进入测得热点的量级 |

### 并发压测的一个观察

同一进程内 8 个并发请求执行「每个快照两次索引探测」这类重查询时，单个查询的墙钟时间从约 4 ms 涨到约 145 ms（8 并发）；同样的 SQL 用 8 个独立进程执行则在 130 ms 内全部完成。单独建 8 个各含 1 个连接的连接池没有改善，说明瓶颈不在连接池或 HTTP 层，而是进程内并发执行大量随机索引探测时的争用（strace 显示约 96% 的系统调用时间在 futex 上）。可复现的基准保存在 `crates/vfiles-infra-sqlite/examples/history_query_bench.rs`（需要自带数据库）。

由此得到的实现约束：请求路径上的查询代价应与「返回给客户端的数据量」相关，而不是与命名空间、快照或历史的规模相关。上面的三处改动都按这个方向收敛；仍需随规模增长的查询见下节。

### 待评估

- **实时目录计数的子树扫描**：嵌套目录的总数需要统计该目录的全部后代。可行方向与快照一致（`entries` 上的派生父路径列 + 索引），但会给条目写入与移动增加索引维护，暂未实施。
- **概览的当前版本探测**：5 万文件的概览仍需约 5 万次「当前版本」索引查询。把当前版本的 `size`/`content_type` 落到 `entries` 上可把概览降到两次索引扫描，但需要在所有写入版本的路径（HTTP、WebDAV、FTP、S3、恢复、删除）上保持一致，风险高于本轮收益，先记录方案与测量。

## 2.9 增量快照基准

50,000 个条目、10,000 次单文件变更、checkpoint interval 1024（release 构建、本地 SQLite/WAL）：

| 指标 | 结果 |
| --- | --- |
| 快照数 | 10,000 |
| checkpoint 行数 | 500,000（10 次全量 checkpoint） |
| delta 行数 | 9,990 |
| 数据库文件 | 约 251 MiB |
| 写入总耗时 | 约 20.6 秒 |

旧模型在同样输入下是每次快照复制 50,000 行，约 5 亿行；新模型只保留 10 个全量基线和
每次变更的 delta。基准测试位于 `vfiles-infra-sqlite` 的
`benchmark_50k_entries_10k_snapshots_stays_incremental`，默认 `#[ignore]`。

### 裁剪旧快照

旧实现逐快照统计 blob 引用，再把所有待删快照放进一个事务；在 85M 行 legacy 数据上会形成
N 次全量聚合和一个超大 WAL。现在改为：

- 每批最多 64 个快照，按批聚合 `snapshot_entries` 与 `snapshot_entry_changes` 的 blob 引用；
- 每批一个删除事务并释放引用，进程中断可重跑；
- 孤儿 blob 清理使用 `blobs.ref_count > 0`，不再对 85M 行快照表做 `UNION` 去重。

注意：删除 85M 行本身仍是主要成本，批量只避免长事务和重复扫描；不会把删除变成瞬间完成。

### 离线重建

`rebuild-snapshots` 不再逐行删除：它创建新的 `snapshot_entries` 表，只复制保留快照的行，
然后替换旧表；完成后重算 blob 引用并可选 `VACUUM`。对“保留很少、旧 legacy 数据很多”的
场景，复制 6M 行通常比删除 78M 行快一个数量级。代价是需要停机、额外磁盘空间和一次性
VACUUM。

## 第四轮：自动快照合并（可选，已被 2.9 增量快照取代）

> **2.9 起**：快照改为 checkpoint + delta，普通写入不再复制整棵树；
> `VFILES_SNAPSHOT_COALESCE_SECONDS` 已废弃。本节保留为历史测量记录。

第三轮确认写入成本来自「每次变更复制整棵树」的模型。本轮按产品决定实现可选的合并窗口，
默认关闭，不改变现有语义。

测量环境同前（50,110 条目、40 个快照、2,004,400 条快照条目；release、本地回环、WAL）。

| 场景 | 关闭合并 | 开启合并（窗口 1 秒） |
| --- | --- | --- |
| 连续上传 6 个小文件 | 6 次快照，逐个约 1.4 s，合计 8.9 s | 首次 2.77 s（含快照），其余 5 次各 7–11 ms，窗口结束后补提交 1 次；合计约 2.8 s + 1 次后台快照 |
| 产生的自动快照 | 6 条 | 2 条（窗口起点 + 合并补提交），补提交包含全部 6 个文件 |
| 手动快照（`POST /api/files/snapshots`） | 立即生成 | 立即生成（不参与合并） |

实现要点：

- 合并状态按命名空间维护：窗口起点立即创建快照，窗口内后续变更只累加待提交计数，窗口结束时
  由后台任务补提交一次（描述为「自动快照（合并 N 次变更）」）。
- 补提交失败保留计数，不忙循环重试；下一次变更重新开启窗口。
- 后台任务在补提交时持有命名空间级状态锁的短临界区，创建快照本身不在锁内，避免阻塞其它
  命名空间的变更判定。
- 配置 `VFILES_SNAPSHOT_COALESCE_SECONDS`（0 表示关闭，上限 3600 秒）。

已知取舍：窗口内的多次写入只保留一条自动快照，历史粒度变粗；进程在窗口结束前退出时，最后一次
变更可能要等下一次变更才进入历史（数据本身已提交）。默认关闭，需要批量写入的部署可自行开启。

## 第三轮：写入侧与维护任务

测量环境同第二轮（50,110 条目、40 个快照、2,004,400 条快照条目，约 1.4 GB；release 构建、本地回环、WAL）。

| 操作 | 审核发现 | 改动 | 修复前 → 修复后 |
| --- | --- | --- | --- |
| 快照裁剪（`vfiles maintenance prune-snapshots`） | 每条快照先把全部条目读进内存（逐行解析 UUID/时间戳）只为统计 blob 引用，再单独提交删除；35 条快照（1,750,000 行）耗时 42.2 s | blob 引用改为 SQL `GROUP BY` 聚合；同一命名空间内本轮要删的快照合并为一次事务删除，引用扣减合并为一次 | 42.2 s → 21.1 s（约 2 倍） |
| 冗余索引 | `idx_snapshot_entries_snapshot_id` 与主键 `(snapshot_id, entry_id)` 前缀重复，只增加整树复制的写入与磁盘成本；2M 行约占 100 MB | 迁移 `0033` 删除该索引；按快照 id 的查询改走主键，`ORDER BY entry_path` 仍走 `(snapshot_id, entry_path)` | 每个 5 万条目快照的复制少维护一个索引；释放约 5% 的表空间 |
| 快照整树复制（未改语义） | 50,110 条目的快照：复制 1.1–1.6 s，提交 0.15–0.6 s（WAL 检查点在其中）；HTTP 上传端到端 2.34 s。批量导入（FTP/CLI）已按阈值合并快照，HTTP 上传仍是每个文件一次 | 评估了插入顺序、`temp_store`、`cache_size`、`wal_autocheckpoint`：缓存 64 MB 约省 8%–16%，但 10 个连接的内存代价过高；关闭自动检查点只把提交成本推迟到后台（提交 136 ms，事后检查点 1.9 s），需要额外的后台检查点任务 | 未改；记录测量与可选方向 |

### 第三轮结论

- 写入侧的主要成本来自「每次变更复制整棵树」的模型本身，而不是查询或索引细节。可选的演进方向：增量快照（记录变更集合并按快照回放）、合并短时间窗内的自动提交（需要延迟/后台快照任务）、或让 HTTP 上传支持一次请求多个文件并共用一次快照。
- 进程内并发重查询的塌陷（第一阶段记录）与 WAL 或页面缓存无关：`mmap_size=256MB`、`cache_size=64MB` 对 8 并发下的总数查询几乎没有改善（178 ms → 151/131 ms），因此缓解手段仍然是把单次请求的工作量收敛到返回数据量。

## 第二轮：实时目录列表、侧栏概览与快照写入

测量环境：release 构建、本地回环、`journal_mode=WAL`；合成库为 50,110 个条目（10 个根目录 × 10 个子目录 × 500 个文件）、40 个快照（2,004,400 条快照条目，约 1.14 GB），并额外写入 100,000 条审计记录、5,000 条分享与 500 条收藏。数字为本机样本，不能作为生产 SLA。

| 操作 | 审核发现 | 改动 | 修复前 → 修复后（p50） |
| --- | --- | --- | --- |
| 实时目录列表（`GET /api/files/list`） | 直接子项用 `LIKE 'prefix/%'` 加 `instr(...)` 过滤整棵子树：根目录分页 6.3 ms，含 5,010 个后代的目录计数 7.1 ms，均随子树规模增长；目录选择器同样扫描 | `entries` 增加派生列 `parent_path` 与 `(namespace_id, parent_path, kind, path)` 索引；计数、分页、游标分页与目录选择器改为一次索引 seek，索引顺序即「目录优先 + 路径升序」。游标分页的六条按类型拆分的语句合并为首页与行值游标两条 | 根目录 3.5 ms → 0.52 ms；含 5,010 后代的目录 5.8 ms → 0.50 ms；8 并发 340 → 3,228 req/s |
| 侧栏概览（`GET /api/files/overview`） | 每个文件都要按主键取一次当前版本（5 万文件约 69 ms），页面加载与每次变更后的侧栏刷新都会触发 | `entries` 增加 `current_size`/`current_content_type`，由 `entry_versions` 的插入/删除触发器维护（直接写 SQL 的路径同样覆盖）；概览聚合不再 JOIN 版本表 | 69.9 ms → 25.5 ms；8 并发 10.5 → 165 req/s；每次版本插入的触发器开销约 0.01 ms |
| 审计日志列表（`GET /api/audit/logs`） | 无筛选时仍使用带 `? IS NULL` 分支的通用计数语句，100,000 行需要 87 ms | 无筛选时走最窄的 `SELECT COUNT(*) FROM audit_logs` | 87.5 ms → 34.6 ms（SQL 层） |
| 快照写入（每次变更复制整棵树） | 50,110 个条目的快照：`INSERT … SELECT` 1.19 s，提交 0.44–0.59 s；HTTP 上传端到端 2.34 s。删除冗余索引 `idx_snapshot_entries_snapshot_id` 仅省约 7%，不值得 | 记录现状与选项，未改语义 | 未变 |

### 已评估、暂不实施

- **快照写入的整树复制**：快照模型是「每次变更复制整棵树」，成本与树大小线性相关。可选方向是增量快照（记录变更集合并按快照回放）或合并短时间窗内的自动提交（会降低历史粒度），两者都改变历史语义，需要单独设计。
- **搜索的并发特性**：8 并发下文件名搜索约 42 req/s，受服务端候选数量与读取预算约束，属于有界扫描的预期成本；单纯加索引无法消除。
- **实时列表的单页成本**：500 个文件的目录一页 200 条约 3.9 ms，其中主要是 JSON 序列化与版本批量查询（每页一次 `IN` 查询），已与目录规模脱钩。

## 已实施的改进

| 问题 | 审核证据 | 改进 | 验证 |
| --- | --- | --- | --- |
| HTTP/2 小包发送延迟 | 本地复用连接请求 27.6 KB 目录 JSON 时，HTTP/2 总耗时 p50 为 45.42 ms、p95 为 46.89 ms；临时启用 `TCP_NODELAY` 后分别为 2.43 ms、3.65 ms。HTTP/1 对照 p50 为 2.35 ms 和 2.05 ms。 | 接受 TCP 连接后启用 `TCP_NODELAY`。设置失败时记录警告，不中断连接接入。 | `http_server::tests::accepted_streams_enable_tcp_nodelay` 检查 socket 选项；HTTP 服务端测试覆盖连接上限、超时和 HTTP/2 设置。 |
| 目录选择器 COUNT 扫描 | 100,000 条目数据集上，查询计划此前按命名空间扫描非覆盖索引。临时复合索引对照测试的 40 次串行请求中，p50 从 28.74 ms 降至 2.27 ms，p95 从 32.16 ms 降至 3.70 ms。 | 添加只包含目录的部分索引，并为根目录目录计数添加更窄的部分索引。 | 查询计划测试要求目录计数使用覆盖索引；完整 SQLite 测试覆盖迁移。 |
| 文件名子串搜索扫描 | 临时 SQLite 3.45.1、300,000 条路径对照：紧凑 trigram 索引将无匹配查询 p50 从 27.13 ms 降至 0.22 ms，将 20 项匹配查询从 24.93 ms 降至 0.10 ms；1,000 项匹配查询从 28.97 ms 降至 8.16 ms。完整细节索引额外占 32.6 MiB；`detail=none` 索引额外占 13.4 MiB（基础数据库 32.6 MiB）。 | 新增默认关闭的 `VFILES_SEARCH_FILENAME_TRIGRAM_INDEX=true`。启用后对路径建立紧凑 trigram 候选索引，仍用原 `LOWER(path) LIKE ... ESCAPE` 精确复核，短查询回退原查询；插入、删除、路径更新由事务触发器维护。 | SQLite 集成测试比较索引与原查询的路径结果（大小写、Unicode、引号、LIKE 通配符和短查询），验证目录范围过滤、查询计划使用 FTS 虚表索引、索引创建/重开/更新/删除/关闭。默认仍关闭：合成 5,000 条插入中位耗时从 15.6 ms 增至 111.5 ms（约 7.17 倍），适合读多写少并愿意用写入速度和约 41% 路径数据库空间换搜索延迟的部署。 |

| 预压缩静态资源的冗余打开 | 文件系统静态资源命中 `.br` 或 `.gz` 时，旧流程会先打开未压缩文件，再打开编码变体。 | 先尝试客户端可接受的 `.br`、`.gz` 变体；变体未命中时再打开未压缩文件。仍对每个文件执行 canonical path 检查。 | 静态资源测试覆盖仅有压缩变体、编码协商、拒绝未压缩内容和越界符号链接。 |
| 每个 HTTP 请求写两条访问日志 | 本地每秒 1,000 次健康检查的对照中，默认日志约 9,517 req/s，关闭 INFO 后约 9,585 req/s；p95 分别为 0.111 ms 和 0.086 ms。默认日志约为每 1,000 个请求 234 KB。 | 合并为一条结构化完成事件，记录请求 ID、方法、脱敏路径、状态码和 `response_ready_us`。该时长到 handler 返回响应为止，不代表响应体传输完成时间。 | 请求日志测试捕获 tracing event，要求每个请求只写一条事件并包含时长字段；原有凭据脱敏测试继续运行。 |

目录计数索引缩小了扫描范围，但会增加少量索引存储和条目写入成本。游标分页消除了分页查询对先前页行数的重复跳过；为保持现有「已加载数量 / 总数」界面，游标请求仍查询精确总数。根目录计数现在只扫描根条目索引，条目数很大的根目录仍会产生与根条目数相关的计数工作。

## 已评估并保留现状的优化项

| 项目 | 当前证据 | 处理依据 |
| --- | --- | --- |
| 连接池和并发上限调优 | HTTP 活跃连接上限为 512、HTTP/2 单连接并发流上限为 32、API 处理许可为 128；SQLite 最大连接数明确固定为 10。256 个并发 HTTP/1 大列表请求中，206 个返回 200、50 个快速返回 429，突发后请求恢复为 200。另在 100,000 条目合成库上重复两轮连接池矩阵：10→20 个连接使 128 个并发「根计数 + 取 100 行」请求 p50 中位数约从 153 ms 降至 138 ms、p95 从 163 ms 降至 150 ms；64 个并发插入的 p50 从 6.6 ms 升至 11.3 ms、p95 从 19.6 ms 升至 47.9 ms，批次耗时中位数从 56 ms 升至 108 ms。40 个连接读延迟更高、插入 p95 进一步变差。池容量测试验证当前上限为 10。 | 保留 10 个连接作为混合读写折中。20 个连接的读延迟收益约 8% 至 10%，但写入 p95 超过 2 倍、插入批次耗时接近 2 倍；SQLite WAL 仍只有一个写入者，连接增加会加重锁争用。HTTP 并发许可提供过载边界，无证据支持统一提高服务级限制。 |
| API 列表、搜索和历史响应缓存 | API JSON 默认使用 `private, no-store`；文件和缩略图使用 `private, no-cache` 并支持条件请求。集成测试验证 session、目录列表、搜索和令牌响应的策略。 | 保留当前策略。列表、搜索和历史结果依赖用户、命名空间、目录和版本状态；缓存命中仍需生成或验证实体标签，并维护跨修改路径的失效规则。没有服务器 CPU 瓶颈证据支持增加这些工作。 |
| 静态资源缓存与前端包体 | 带哈希的资源缓存一年并标记 immutable，`index.html` 使用 `no-cache`。当前构建检查通过；Brotli 为 804.6 / 833.8 KB、gzip 为 878.1 / 912.6 KB、未压缩为 1,927.3 / 2,026.1 KB，均已使用约 95% 至 97% 的现有预算。 | 保持当前缓存策略和体积检查。缓存已经利用资源哈希保证版本隔离；包体余量较小，新增依赖前继续检查预算。 |
| 根目录精确总数的维护计数 | 100,000 条目对照中，根列表 p50 / p95 为 8.63 / 10.87 ms；计数查询计划已使用只含根条目的覆盖部分索引。并发 32 时整页 p50 / p95 为 102 / 168 ms。 | 保留每页精确计数。串行计数成本已低，维护计数会要求所有创建、删除、移动、批量导入和回滚路径原子更新同一状态；目前没有证据证明它能抵消一致性成本。 |

普通归档 GET 已改为流式输出；Range、条件请求仍用临时文件生成。上表已逐项记录其余候选的本地数据和保留现状的理由。文件名 trigram 索引提供默认关闭的开关，启用前应安排回填时间并确认磁盘余量和写入比例。

## 当前关键资源限制

| 资源 | 当前限制或行为 |
| --- | --- |
| HTTP 连接 | 最多 512 个活跃连接；超限的新连接会关闭。 |
| HTTP/2 | 每个连接最多 32 个并发 stream；接受的 TCP socket 启用 `TCP_NODELAY`。 |
| API 处理 | 全局 API 处理许可为 128；饱和时快速返回过载响应。 |
| SQLite | WAL、`synchronous=NORMAL`、5 秒 busy timeout；连接池最大连接数为 10。 |
| 前端静态文件 | 文件系统模式按请求 canonicalize 文件并检查其仍处于前端根目录下；优先读取预压缩文件。 |
| ZIP 归档 | 普通 GET 使用容量为 2 的有界响应 channel 和 64 KiB 块；Range / 条件请求会完整写入临时文件，以提供已知长度和 seek。 |

不要只根据并发请求数提高连接、stream 或 API 许可。SQLite 写入能力、文件系统吞吐、CPU 和内存都会限制实际容量。
