# 提案：移动端长按拖拽（交互草案）

> 状态：**✅ 已决策 → 实现 F（长按多选）/ E 不做**（用户拍板 ✗ B+ = 移动唯一多选路径 ✓）。原稿（round 98）。与 PROPOSAL_OVERWRITE_UPLOAD / 平移钳制
> 同列（决策总览见 PROPOSAL_INDEX.md）。

## 1. 现状

移动无原生拖拽（HTML5 DnD 触屏不支持 ✓）——现状以**行操作菜单「移动到…」**为
主导交互（精确、可发现 ✓）。桌面端已有完整拖拽三部曲（跟随 chip / 两段式 /
三态禁止 ✓ r57-59）+ 落子回执（r61）。

## 2. 主流对照

| 产品 | 移动拖拽 |
| --- | --- |
| iOS 文件 / Finder iOS | 长按 350ms 浮起 + 拖拽（系统级） |
| Google Drive 移动 | **菜单主导**（移动到…）+ 长按多选 ✓ |
| Dropbox 移动 | 菜单主导（移动） |
| OneDrive 移动 | 长按进入选择 + 菜单移动 |

**结论**：菜单主导 = 主流稳健派 ✓ 长按拖拽 = 体验增强派（平台级手势派）。

## 3. 方案

| 案 | 内容 | 工作量 | 风险 |
| --- | --- | --- | --- |
| **A 长按拖拽** | 350ms 浮起（transform 抬升 + 影子）→ 拖拽 → 复用桌面 chip 三部曲 + 落子回执 ✓ | ≈1 轮 | **touch × 滚动冲突**（经典险 ✗ 拖拽与列表滚动手势争用 ✓ 需 touch-action/长按定时器/取消边界全套） |
| **B 菜单主导（现状）** | 保持「移动到…」+ 可加**长按 = 多选**（Drive/OneDrive 式 ✓ 与批量条衔接 ✓） | ≈0.3 轮 | 低（菜单/多选 = 既有件组合 ✓） |

## 4. 推荐

**B 为主**（菜单精确 + 主流稳健 ✓）**+ A 可选后置**（体验增强 ✓ 待 B 后再评估
手势险）。**长按 = 多选**（B+）为中间甜点：手势简单（无拖拽滚动冲突 ✓）、
与批量条/移动菜单链路全复用 ✓。

## 5. 决策点

- [ ] E. 是否做 A（长按拖拽）？（推荐：暂缓，先 B+）
- [ ] F. 是否做 B+（长按多选）？（推荐：做 ✓ 0.3 轮）
