# 提案：覆盖上传（版本化替换）交互草案

> 状态：**待产品决策**（round 55 出稿）。背景见 §4.41/§4.57——同名上传现被
> 「目标路径已被占用」拒绝，内容版本只能靠 import/移动/历史恢复产生。

## 1. 主流方案对比

| 产品 | 同名上传行为 | 选项 |
| --- | --- | --- |
| Google Drive | 冲突对话框 | **替换**（覆盖为新版本）/ 保留两个（自动加后缀）/ 取消 |
| Dropbox | 自动改名「名字 (1)」| 可在设置中改为逐次询问 |
| OneDrive | 同 Drive 三选项 | 替换即覆盖 |
| Box | 询问（可默认保留版本） | 替换 = **自动存为新版本** ✓ 与我方模型同路 |

## 2. 我方差异化卖点

**「替换 = 生成新版本，历史永不丢失」**——版本控制原生语义（Box 同路、Drive 需开
版本历史才保住旧文件）✓ 对用户的话术：**覆盖不等于删除**。

## 3. 交互草案（阶段一：覆盖上传）

```
上传（拖放/选择器） → 检测同名 → [冲突对话框]
  ┌────────────────────────────────┐
  │ 名称已被占用：项目库/说明.md        │
  │ 该文件已有版本历史。继续将生成新版本，  │
  │ 旧版本可随时在「历史版本」中恢复。    │
  │                                │
  │ [替换（生成新版本）] [保留两个] [取消] │
  └────────────────────────────────┘
```

- **替换（生成新版本）**= 主行动（accent）✓ 走现有 `/files/upload` + 新增
  `overwrite: "new-version"` 参数（后端单点：冲突时落 `entry_versions` 新行 ✓
  已有模型，无表结构变更）；
- **保留两个**= 现行语义的安全档：自动改名 `说明 (1).md`（Dropbox 模式 ✓）；
- **取消**= 关闭对话框、上传队列该项标记「已跳过」（DownloadQueue 风格 ✓）；
- 批量冲突：列表式对话框逐项三选 + 「全部替换/全部保留两个」快捷钮（Drive 批量式 ✓）。

## 4. 行为细节

1. 冲突检测时机：**上传入队时**（前端已有列表数据可预判 ✓）+ 服务端最终裁决
   （并发下以服务端 409 + 冲突载荷为准）；
2. 版本消息：自动生成「上传替换：<文件名>」（可选填写备注框 = 与历史恢复同款 ✓）；
3. toast：成功「已替换并生成新版本」（与「已恢复并生成新版本」话术成族 ✓）；
4. 权限/分享不受影响（entry 不变、仅新增版本 ✓）；
5. 移动端：底部抽屉式三选（M3 bottom-sheet 语言 ✓）。

## 5. 阶段二（编辑器）——暂不建议同期做

在线编辑 = 新组件族（编辑器工具栏/保存态/冲突合并）× 双主题 × 可访问性 ≈ 一轮半
工作量起；建议**先上阶段一**（覆盖上传已解决 90% 的"更新文件"诉求 ✓ 数据佐证：
版本生成三路径中 import/移动均是批处理，缺的正是单文件更新入口）。
